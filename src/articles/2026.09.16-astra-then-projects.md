## GPT-6 Astra: the new $10 / $50 ceiling

**Astra is the new frontier price band to quote against, not the default for every draft.** Use it when computer use, long-context coding, or a hard agent loop is the job. Keep cheaper Flash lanes for volume. Approvals still matter on send, pay, and publish.

## Cursor Projects: coordinator, shared context, subscriptions

**Put one bounded, recurring job in a Project — not your whole codebase.**

**[Cursor Projects entered beta 10 September 2026](https://cursor.com/blog/projects).**
This is a product layer above single chats and one-off agents: a
**coordinator** directs cloud (and local when needed) subagents, keeps
**shared Project context** across months, and supports **subscriptions**
(Slack, schedule, PR/CI). Cursor describes internal use for migrations and
design-system upkeep.

Cursor cites new users merging **30% more PRs**, and users who primarily
use Projects merging **six times as many** *(vendor)*. Treat those as leads,
not measurements.

**What this means for you:** Projects is for work that repeats — a weekly cleanup, a slow migration — where the agent benefits from remembering last month. One-off questions still belong in a normal chat.

# Part 2: Mini-lessons

## Mini-lesson: Skills, Agents, and Memories

*An educational taxonomy for agentic systems. The [Agent Skills project](https://agentskills.io/home) and [specification](https://agentskills.io/specification) confirm an open format and `SKILL.md` structure. Statements about statelessness, RAG, and memory below are practical framing, not universal definitions: harnesses can persist context, and retrieval can operate over writable memory.*

These three words get used like synonyms. They are not. In a working agentic system they sit on different layers of the same stack — and confusing them is how you ship a stuffed system prompt that behaves like amnesia.

**Agent** — the runtime. A model wrapped in a loop that can pursue a goal, use tools, observe, and decide whether to keep going.

**Skill** — the playbook. Packaged procedural knowledge — instructions, judgment, optional scripts — loaded only when the task matches.

**Memory** — the persistence layer. Facts, preferences, and past events that survive a single model call, then get written back.

### A new hire on day one.

1. **The agent is the hire.** They have a mandate, a desk, tools, and a loop: look, think, act, check whether the job is done. Without that loop they are just sitting in Slack.
2. **A skill is the SOP binder.** “When someone asks for a refund, follow these steps. Use this template. Do not invent policy.” They pull the right folder when the task shows up.
3. **Memory is the scar tissue.** Everything learned after day one. This customer already got a courtesy credit. This repo uses pnpm. Last deploy died because someone edited the env file by hand.

### One ticket. Three layers.

**Refund this customer.**

**Memory recalls** — what is already true: Enterprise plan. One courtesy credit granted in March. Do not pretend this is the first conversation.

**Skill loads** — the refund playbook: eligibility, approval threshold, tone, which fields to log. Policy that should not be improvised.

**Agent decides** — then acts: pulls the order through a tool, applies the playbook to the remembered facts, refunds or escalates.

**Yank memory** — amnesiac intern. Re-asks everything. May issue a second courtesy credit.

**Yank skill** — improvises policy. Sometimes generous, sometimes illegal, never consistent.

**Yank agent** — a well-written PDF that cannot click Submit.

### What each one actually is.

**Agent — the runtime**

An agent is a system, not a model. The model reasons. The agent *does*. Autonomy is the distinguishing property: a chatbot that answers once is not an agent, and a script that always calls the same tool in the same order is a workflow. An agent chooses the next move based on what just happened.

A sub-agent is the same idea with isolation: a worker spawned with its own context window, its own prompt, and a smaller mandate. A skill is not a sub-agent. A skill is instructions. A sub-agent is a worker.

**Skill — the playbook**

One widely used format is the Agent Skills standard — a folder with a `SKILL.md` file plus optional scripts, templates, and reference files. The format is an open spec. Skills can include real code, because for “normalize this spreadsheet” a script is more reliable than asking the model to improvise bytes.

Skills answer a narrow question: *how should I perform this kind of work, here?* They are not workers. They do not spawn themselves. They do not remember the user.

**Memory — the persistence layer**

Memory answers two questions the context window cannot: what is true about this user or domain, and what already happened. If it never writes, you built a search index and called it learning.

| Kind | Focus | What it holds |
| --- | --- | --- |
| Working | Now | The context window. Recent turns, the tool result you just got. Harnesses can retain and replay that context across calls. |
| Episodic | What happened | “On March 3 they asked to downgrade.” Timestamped events, across sessions. |
| Semantic | What is true | “Customer is on the Enterprise plan.” Facts and preferences, slowly changing. |
| Procedural | How to do it | Learned workflows. This is where skills live when you externalize them as files. |

A useful contrast: RAG (retrieval-augmented generation — searching your documents and pasting the hits into the prompt) searches a corpus; memory stores what this agent accumulated and can write back. That is not a universal boundary — RAG can retrieve agent-written memories, and memory can include read-only stores. The useful engineering questions are who writes, who retrieves, what persists, and which trust rules apply.

> **Why the model is not the memory.** A useful simplification: the model itself does not automatically keep durable user memory. Continuity is an engineering layer you add around it — retrieved into working memory, then written back when something is worth keeping. That does not mean a call has no prompt, prior context, or cached state.

> **Progressive disclosure.** A good skill system loads only a name and description at startup. The full playbook comes in when the task matches. Thirty skills can sit on the shelf. You pay for the two that matter this turn.

### They are not alternatives.

An agent uses skills and memories. Skills do not run themselves. Memory does not execute.

| Layer | Primitive | Lives in | Question it answers |
| --- | --- | --- | --- |
| Agent | Control loop, identity, permissions | Runtime / harness | Who is acting, and with what autonomy? |
| Skill | On-demand procedure | Files — SKILL.md + resources | How do I do this kind of work? |
| Memory | Persistent state | External store + context window | What do I know, and what happened before? |
| Tools | Actuators | Function schemas / MCP | What can I touch in the world? |

```text
goal arrives
  → assemble working memory
      (prompt + recent turns + retrieved memories + skill index)
  → match the task to a skill
  → retrieve the relevant facts / episodes
  → plan, call tools, observe
  → write new memories
      (facts learned, outcomes, corrections)
  → if the work needs isolation: spawn a sub-agent
```

### A practical order of operations.

**Write a skill** when the procedure is known and repeatable — code review, refund rules, how you make a deck. You are tired of re-explaining it. You want it versioned in git and loaded only when relevant.

**Add memory** when facts, preferences, or events must survive the session, and when the system should write back what it just learned. If it only reads, you built search.

**Build an agent** when the next action depends on observations. Multi-step work, tools, a stop condition. Skills and memory are what make that loop useful the second time you run it.

Starting with “we need an agent fleet” usually produces a chatbot with a job title. Encode the playbook first. Persist the few facts that actually matter. Then wrap both in a loop.

### Adjacent terms

**Tools / MCP** — give access. A database connector lets the agent query billing. A skill tells it which query pattern to use, what “eligible” means, and what to do when the row is messy. Access is not judgment.

**System prompts & AGENTS.md** — standing instructions that load every session: repo conventions, taboos, how to run tests. Keep them short. If a procedure is only sometimes relevant, it belongs in a skill, not in the always-on file.

**Sub-agents** — workers with their own context windows. Use them for isolation and parallelism. Use a skill when the current agent needs a playbook. Multi-agent setups often cost several times the tokens of a single loop.

**Procedural memory** — in a cognitive taxonomy, skills are procedural memory externalized. In engineering, keep the storage separate: skills are versioned playbooks; memories are accumulated state that can go stale. Related layers. Different lifecycles.

### Ten ways this goes wrong.

1. **Calling a chatbot an agent.** One reply is not agency. If it cannot observe a tool result and change its next move, it is a function with a personality.
2. **Stuffing procedures into memory.** “Remember how we deploy” becomes folklore. Put the procedure in a versioned skill.
3. **Stuffing facts into skills.** A playbook that hard-codes the user’s name is a diary. Skills should still be right if the user changes.
4. **Treating RAG as memory.** Different write path. Different owner. Different failure mode.
5. **Treating tools as skills.** Hands versus training. Tools are verbs. Skills are judgment about when and how.
6. **A stuffed system prompt as a fake hybrid.** Always-on walls of instructions fight each other and get ignored. Working memory is a budget. Treat it like one.
7. **Memory with no forget path.** Stale pricing, stale preferences, confident wrongness. Bad memory makes agents worse, not wiser.
8. **Skills that never fire, or always fire.** Progressive disclosure lives or dies on the description. Too broad → always loaded. Too narrow → never selected.
9. **No write-back.** Read-only “memory” is search. The loop has to extract, store, and later retrieve.
10. **One mega-agent instead of composable skills.** Hard to test, hard to share, hard to debug. Build the skill. Test it. Then let an agent pick it.

> The agent is the hire. The skill is the SOP binder. Memory is the scar tissue.

Build them as three things. Let them talk to each other. That is the difference between a demo that answers once and a system that still knows what it is doing next Tuesday.

## Mini-lesson: Origin vs GitHub

*A short field guide on Cursor’s git host, mostly useful if you already work in Cursor. [Cursor’s Origin docs](https://cursor.com/docs/origin) confirm early beta, paid-plan staged access, standard Git, and hosted/mirrored modes. [Cursor’s August 14 announcement](https://cursor.com/blog/joining-spacex) confirms acquisition by SpaceX.*

> **Two forges, one git.** Origin is Cursor’s git forge; GitHub is Microsoft’s. They speak the same git, but they are not the same product — and Origin is not the default git remote that happens to be named `origin`.

GitHub is the public house; Origin is Cursor’s house next door, built so agents and humans share one repo surface. You can keep a key to both.

### A git forge inside Cursor.

Current Cursor docs confirm early beta and paid-plan access.

**Codebase tab** — `cursor.com/codebase`

**Clone** — standard git: `origin.cursor.com/{owner}/{repo}.git`

**Access** — paid only: Pro, Teams, and Enterprise. No free tier in beta.

### Why Grok and xAI come up.

Cursor announced on August 14 that it is joining SpaceX, which also makes the Grok models through SpaceXAI (formerly xAI) — so Cursor and Grok are now in the same corporate family. Origin is still a Cursor product, not a Grok feature: Grok is the model and the agent; Origin is where the git repo can live. Agents attach to Origin remotes; they do not replace GitHub by themselves.

### How they are similar.

Both are git forges, so the everyday verbs do not change.

**Git** — same protocol: clone, push, pull, branches, tags. Ordinary git over HTTPS.

**Review** — pull requests: diffs, comments, checks, merge. Mirror documentation supports GitHub PR review in Cursor.

**Agents** — both assume AI. GitHub layers Copilot on a human forge. Origin puts agents on the same surface as the code.

### How they differ.

| Question | Origin | GitHub |
| --- | --- | --- |
| What it is | Cursor’s built-in git host (early beta) | The default public code platform |
| Who owns it | Cursor (SpaceX acquisition) | Microsoft |
| Who can use it | Paid Cursor plans, staged rollout | Anyone, including a large free tier |
| Designed around | Many agents committing in parallel | Human-paced teams, AI added later |
| Missing in beta | Issues, native Actions, public OSS | Core forge features are mature |
| CI / deploys | Apps including Vercel, Depot, Buildkite | GitHub Actions + marketplace |

Confirm current integration support before migrating.

### A repo can live two ways.

**Origin-hosted** — You create it in Cursor. Origin is the source of truth. Pushes land on Origin. GitHub is not in the path.

**Mirrored from GitHub** — GitHub stays the source of truth. GitHub branches named `origin` or `origin/...` do not sync; forge-local branches have a separate write path. The docs confirm GitHub PR review in Cursor, and that Issues, Actions and secrets stay on GitHub. Detaching makes Origin the source of truth without affecting the GitHub repository. [Read the current mirror behavior](https://cursor.com/docs/origin/mirror-github) before changing a remote.

### Competitors, and complements.

**Stay on GitHub when** you need the commons — public network, Issues, Actions, packages, or a host every vendor already speaks.

**Try Origin when** the repo should sit next to the agent — greenfield work started in Cursor, or a GitHub mirror you review and merge without leaving the editor.

Mirroring is the default path. A full switch only happens when you create an Origin-hosted repo, or Detach a mirror.
